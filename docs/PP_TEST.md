# ピュアパシュートの使い方（pp_test.py と LINE_ALGO）

ハンドルの新方式「ピュアパシュート」の準備・確認・切り替えの手順です。
方式を選んだ理由と比較の結果は `docs/LINETRACE_EVAL.md` にあります。

## 全体の流れ

1. `pp_test.py` でキャリブレーションする（最初に 1 回）
2. `pp_test.py` で見え方を確かめ、値を調整する
3. 今の方式のまま走って、走行記録で 2 つの方式を見比べる（見るだけモード）
4. 方式を「ピュアパシュート」に切り替えて走る

`pp_test.py` はハンドルもモーターも動かしません。計算と表示だけです。

## ファイル

| ファイル | 役割 |
|---|---|
| `line_algo.py` | ピュアパシュートの部品（画素⇔床の変換、点群の検出、ハンドルの計算） |
| `pp_test.py` | キャリブレーションと確認の画面 |
| `rc_race.py` | 本番。`LINE_ALGO` で方式を切り替える |
| `tools/linetrace_sim/gazou_test.py` | 合成したカメラ画像で、実物のプログラムのまま 1 周させる試験 |

## 1. キャリブレーション

カメラの画面の位置と、床の上の位置[m]の対応を覚えさせます。
カメラの向きや高さを変えたら、やり直してください。

用意するもの：マスキングテープ、メジャー

1. 床にテープで四角形を作る。目安は横 40cm × 奥行き 60cm。大きいほど遠くまで正確になる
2. 四角形の左右の中心を車の中心線に合わせ、車をまっすぐ向けて置く
3. 後輪の車軸の中心から、四角形の手前の辺までの距離を測る（四角形が画面に全部映る位置に置く）
4. ラズパイで `python3 pp_test.py` を起動し、ブラウザで `http://<車のIPアドレス>:8080` を開く
5. 「開始（映像を止める）」を押し、映像の上で四角形の 4 つの角をクリックする（順番は自由。5 回目を押すと最初からやり直し）
6. 横幅・奥行き・車軸からの距離を入力して「計算して保存」

保存すると「真上から見た図」が出ます。次を確かめてください。

- オレンジの枠が、床の四角形のテープと重なっている
- 床の四角形が、ゆがまずに四角に見える
- マス目（10cm）と、床に置いたメジャーの目盛りが合っている

合っていなければ、寸法の入力か、クリックした角がずれています。やり直してください。

画面の上に「見える範囲」が出ます。**2.5 m/s で走るなら、約 1m 先まで見えている必要があります。**
足りないときは、カメラをもう少し上向きにしてキャリブレーションし直します。

## 2. 見え方の確認と値の調整

車をラインの上に置くと、次のものが表示されます。

- 水色の点：見つけたライン（点群）。車を中心にした同心円に沿って探すので、ラインが横向きになっても追える
- 水色の線：先読みの円（半径＝先読み距離）
- 赤紫の丸：目標点。先読みの円とラインが交わる所
- 赤紫の線（真上から見た図）：目標点へ向かう円弧。この円弧のとおりにハンドルを切る

「いまの計算結果」に、今の方式とピュアパシュートのハンドルが並んで出ます。
車を手で左右にずらしたり、カーブの手前に置いたりして、違いを見比べてください。

### ラインのしきい値（最初に合わせる）

「白黒で見る」を押すと、映像が「ラインと判定した所だけ白」の白黒になります。
ラインだけが白く、床や照明の映り込みが黒くなるように、「ラインのしきい値」のスライダーを動かしてください。

- 白線（`LINE_IRO = "shiro"`）：`SHIRO_SHIKII`。これより明るい所がライン。映り込みまで白くなるなら上げる、ラインがかすれるなら下げる
- 黒線（`LINE_IRO = "kuro"`）：`KURO_SHIKII`。これより暗い所がライン。影まで白くなるなら下げる、ラインがかすれるなら上げる

この値は今の方式とピュアパシュートの両方に効きます。会場の照明で決まる値なので、授業用と同じく「値を保存する」で**共通設定 `kyotsu_settei.json`** に保存されます（ほかの値は `kuruma_settei.json`）。
`kuruma_settei.json` に同じ名前の値があると共通設定より優先されてしまうので、保存のときに自動で消します。

`kyotsu_settei.json` は Git で管理しているファイルです。ラズパイで保存した値を残すときは、ノートパソコン側にも同じ値を入れて commit してください（Claude Code に「ラズパイの kyotsu_settei.json の変更を取り込んで」と頼めば、その作業をしてくれます）。

### 調整できる値

| 値 | 意味 | 大きくすると | 小さくすると |
|---|---|---|---|
| 先読み距離の基本 `PP_LD_KIHON` | 何m先のラインを狙うか | なめらか。蛇行をならす。カーブの内側を通る | ラインに忠実。ふらつきやすい |
| 速度 1m/s あたりの伸び `PP_LD_SOKUDO` | 速いほど遠くを見る量 | 高速で安定 | 高速でふらつきやすい |
| アクセル 1% あたりの速度 `PP_SOKUDO_KEISU` | 速度の見積もり（センサーが無いため） | 先読みが伸びる | 0 なら先読み距離は固定 |
| ハンドル 1.00 の切れ角 `KIREKAKU_DO` | 左右いっぱいのときの前輪の角度 | 切り足りず外にふくらむ | 切りすぎてふらつく |
| カーブでアクセルを緩める強さ `PP_CURVE_GEN` | カーブの手前の減速 | カーブで遅く・安全 | 0 なら減速なし |

スライダーを動かすとすぐ図に反映されます。気に入ったら「値を保存する」を押します（`kuruma_settei.json` に保存され、本番にも反映されます）。

### 最初に測っておく値

- **`KIREKAKU_DO`（切れ角）**：`servo_test.py` で「左いっぱい」「右いっぱい」にして、前輪の角度を分度器で測る。左右の平均を入れる
- **`PP_SOKUDO_KEISU`（速度の見積もり）**：決まった距離（例：5m）を一定のアクセルで走らせて時間を測り、速度 ÷ アクセル% を入れる。分からないうちは 0 のままでよい（先読み距離は基本の値で固定）

## 3. 見るだけモード（今の方式で走りながら見比べる）

キャリブレーションが済んでいれば、`LINE_ALGO` が `pd`（今の方式）のままでも、
rc_race.py はピュアパシュートの計算だけをして、画面と走行記録に残します。

- 画面：点群と目標点が薄い色で表示される
- 走行記録（`logs/run_*.csv`）の列：`方式`、`今の方式のハンドル[%]`、`PPのハンドル[%]`、`PP目標の前[m]`、`PP目標の左[m]`、`PP先読み[m]`、`PP点の数`

まずこの状態で何本か走り、2 つのハンドルの値を見比べてください。
確かめること：**左右の向きが同じか**（符号が逆なら設定がおかしい）、ピュアパシュートの値が暴れていないか、点の数が極端に少なくないか。

## 4. 方式を切り替えて走る

rc_race.py または pp_test.py の画面で「ピュアパシュート」を押します（`kuruma_settei.json` の `LINE_ALGO` が `pp` になる）。待機中（IDLE）だけ切り替えられます。

**初めて切り替えたときは、次の順で確かめてください。**

1. 車輪を浮かせた状態で走らせ、車を持ってラインの左右にずらす。ラインに戻る向きにハンドルが切れるか
2. 低いアクセルで短い直線を走らせる
3. カーブのあるコースを低速で走らせる
4. 少しずつ速度を上げる

ピュアパシュートを選んでいても、目標点が決まらないコマ（ラインが近くしか見えない、など）は自動で今の方式に戻ります。
画面の「ハンドルの方式」の下に、いまどちらで走っているかが出ます。

## うまくいかないとき

### rc_race.py で RUNNING になるのに走り出さない

授業用の DragRACE では走るのに DragRACE-S で走らないときは、**車ごとの設定ファイル `kuruma_settei.json` の違い**を疑ってください。
このファイルは Git に入らないので、フォルダごとに別のものがあります（スロットルの向き、学習値、アクセルの強さなど）。
次のプログラムで、2 つのフォルダの違いと、実際に出る信号を比べられます（読むだけで、書き換えません）。

```bash
cd ~/DragRACE-S
python3 tools/settei_hikaku.py
```

「⚠」が出た項目が原因の候補です。DragRACE で走れているなら、その値に合わせるか、DragRACE-S で throttle_test.py をやり直してください。
ESC の電源は、rc_race.py を起動したあとに入れることも確かめてください（pp_test.py は信号を出さないので、その間に入れると覚えるニュートラルがずれることがあります）。

### STOP を押すと思いきり後退する

ブレーキは「後退側の信号」です。車が止まっているときに出すと、ESC は後退として扱います。
2026-11-18 から、STOP ボタン・時間切れ・通信断では、ブレーキを使わず N に戻すだけにしました（`STOP_BRAKE = false`）。
ゴールとラインロストのときは、車が走っていたはずなのでブレーキを使います。走り始めて 1 秒未満のときは、どの止め方でもブレーキを使いません。
走っている車を STOP で強く止めたいときは `STOP_BRAKE` を `true` にします（止まった車で押すと後退するので注意）。

### そのほか

| 症状 | 確かめること |
|---|---|
| 真上から見た図がゆがむ | キャリブレーションの寸法と、クリックした角。四角形を大きくする |
| 点群がラインの途中で終わる | ラインがかすれている／照明。pp_test.py の「白黒で見る」で、ラインのしきい値を合わせる |
| 点群が別の物に飛び移る | 照明の映り込みがラインと判定されていないか白黒で確かめる。しきい値を調整するか、`PP_GATE` を小さくする（初期値 0.25） |
| 「先読み距離に届いていません」と出る | カメラを上向きにする、または先読み距離を短くする |
| カーブで外にふくらむ | `KIREKAKU_DO` が実際より大きい。先読み距離が長すぎる |
| 直線でふらつく | 先読み距離を長くする。`KIREKAKU_DO` が実際より小さい |
| カーブの内側を通りすぎる | 先読み距離を短くする |

## 試験（パソコンでもラズパイでもできる）

```bash
cd ~/DragRACE-S
python3 tools/linetrace_sim/gazou_test.py
```

合成したカメラ画像を使い、rc_race.py のライン検出と line_algo.py を実物のまま動かして、4 種類のコースを 1 周させます（数分かかります）。
プログラムを直したあとに、壊れていないかを確かめるのに使えます。

2026-11-17 の結果（カメラの高さ 0.25m・下向き 30° を仮定）：

- 今の方式：1.5 m/s までは完走、2.5 m/s では全コースで見失い。きつい角のコースは 1.0 m/s でも完走できず
- ピュアパシュート：4 コースすべて、2.5 m/s まで完走
- 計算時間：ピュアパシュートを足しても 1 コマあたり約 1 ミリ秒の増加（パソコンでの値。ラズパイ 4 では数ミリ秒の見込み。実機で fps を確認すること）

## まだできていないこと

- 実機での確認（ここまではすべてシミュレーションと合成画像での確認）
- 速度の実測。今はアクセルの値からの見積もりだけ（エンコーダーか、地図上の位置の変化から出せるようになれば正確になる）
- 「カーブでアクセルを緩める」の実走での調整

## 2026-11-19 追加：足元からたどる検出のスライダー

`LINE_ALGO="pp"` のとき、検出は「足元とつながった塊だけをラインにする」方式になった（詳しくは `PP_KENSHUTSU_20261119.md`）。画面に次のスライダーが増えた。モーターは動かない。

- `PP_SA`：周りの床との明るさの差の下限（共通設定へ保存）
- `PP_HABA_MIN` / `PP_HABA_MAX`：ライン幅の下限・上限 [m]（共通設定へ保存）
- `PP_GATE_Y`：前のコマの位置から左右に探す範囲（車ごとの設定へ保存）
- `PP_LD_CURVE`：カーブで先読み距離を縮める強さ（車ごとの設定へ保存）

「白黒で見る」では、白＝ラインとして選んだ塊、灰色＝選ばれなかった候補になる。

注意：`kyotsu_settei.json` は手で編集しない。初期値はプログラムの中にあり、「値を保存する」を押したときに、必要な項目だけが追記される。
